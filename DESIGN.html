Team Collab 设计书

Design Proposal · Team Collab

让每个 agent 的上下文，
沉淀成团队可复用的资产

团队里的 agent 各自聪明，却在上下文孤岛中工作。Team Collab 以项目为单位打通上下文，用一个专职的 management agent 把讨论、产物、代办与决策维护成一份活的团队记忆——任何 agent 接入即用，用完反哺。

版本 v1.0 · 2026-09-02 状态：核心闭环已在本地 demo 中实现并端到端验证
01

要解决的痛点：上下文孤岛

一个团队里往往同时运行着许多 agent 会话：有人在做调研，有人在整理需求，有人在产出文稿。每个 agent 的输入、过程与产物，都锁在各自隔离的会话与存储里。于是团队只能退回到最低效的对齐方式——开会、写文档、口口相传，让人肉充当 agent 之间的总线。

结果是双重浪费：agent 做过的调研没人能复用，团队已有的结论 agent 也看不见。智能在增长，团队记忆没有。

02

为什么现有知识库救不了它

Wiki、Notion、Obsidian 库当然可以承载团队知识。但它们几乎都会走向同一个结局：维护成本高，堆满没人删的旧页面，更新永远滞后于事实。知识库死掉，不是因为工具不好，而是因为没有人对它的「活性」负全责，也没有一条让知识自动生长的路径。

静态知识库

知识靠人手工搬运进去；只增不删；没有生命周期；写下来的那一刻开始过期；与工作流断开，用的人越来越少。

Team Collab 的回答

知识由工作流自动产出：每一次任务合并都触发一次知识编译；有专职的 management agent 负责替换过期事实而非追加流水账；项目边界天然限定了「什么相关、什么重要」。

换句话说，我们不是再造一个更好的笔记工具，而是给团队上下文配一个全职维护者：一个以项目为单位、统一管理项目代办、产物沉淀与讨论结论的 management agent。任何 agent 都可以接入项目上下文，基于已有积累开展工作，再把成果反哺回来。

03

三个核心理念

团队上下文是最重要的资产。它长在项目文件夹里、进 Git 版本管理，不属于任何一个 agent 会话，也不会随会话关闭而蒸发。

Agent 只是智能插件。Claude Code、Codex 或任何 CLI agent，装上插件即可接入项目空间；换 agent 不丢上下文，多 agent 共享同一份记忆。

Management agent 是上下文的维护者。它不抢工作，只做三件事：把讨论沉淀为代办与知识、守卫式地合并成员产出、把合并结果编译进团队记忆并淘汰过期事实。

04

为什么必须是专职的 management agent

一个自然的反问是：能不能省掉这个角色，让每个成员 agent 完成任务后「顺手」维护团队知识？不能。四个理由：

  1. 竞态问题难解决。多个成员 agent 并发编译同一份团队知识，必然出现相互覆盖、丢失或错乱——这是分布式写入的经典问题，靠约定解决不了。专职 management agent 把知识变更收敛为单一写入者，天然串行化。实现印证：知识只接受 management agent 的全文件提案，且带基线哈希校验，任何并发修改被判为过期而非被静默覆盖。
  2. IM always-on 的上下文收集。讨论沉淀需要一个常驻、跨会话的角色持续监听群聊、按项目目的持续提炼。成员 agent 是任务生命周期内的临时会话，任务结束即消失，没有资格、也没有生命周期承担 always-on 职责。
  3. 维护触发的稳定性。团队知识的沉淀不能寄希望于「每个成员 agent 都记得做、都做得对」。两层保证：其一，触发确定——影响团队知识的 merge 由守护进程按事件强制进入知识编译阶段，一次都不会漏；其二，行为确定——management agent 的 system prompt 与工具面由系统统一下发，不需要赌各家成员 agent 的 prompt 是否遵守编译契约。尤其是长任务之后，成员 agent 自身可能已经 context rot，此时让它编译团队记忆，是在用团队最重要的资产冒险；而 management agent 每次都是短生命周期、全新上下文、重读事实源的运行，不携带任何腐化状态。
  4. 更好的权限管控。成员 agent 无需持有团队记忆的写权限——写路径唯一、身份绑定、全程事件留痕，审计、回滚、审批都收敛在一条通道上。把写权限散给每个成员 agent，等于放弃对核心资产的治理。
05

概念模型：项目粒度 × 四类上下文

为什么以项目为粒度？项目天然自带目的、边界与生命周期。这三样东西正是 management agent 判断「哪些上下文相关、哪些重要、哪些该淘汰」的依据——脱离项目谈知识管理，就回到了堆文档的老路。

项目内的上下文分为四类，各有明确的来源与去向：

讨论Discussions → Inbox
原始材料，发生在 IM 群聊里。由沉淀 agent（用户触发或定时）按项目目的提炼成候选任务与问题，带原文引用与置信度进入收件箱，经人分诊后才生效——类似自动生成的会议纪要，但直接接入工作流。
知识Knowledge
agent 与用户沉淀的结论性产物：项目现状、已定决策、可复用的经验教训与资产索引。是每个新任务的背景与参考，由 management agent 在每次合并后编译维护，替换过期事实而非无限追加。
代办Tasks
团队共有的待办事项。有完整状态机（草稿 → 就绪 → 认领 → 进行中 → 已提交 → 集成中 → 完成），原子认领防止撞车，全team可见。
开放问题Open Questions
需要团队共同智慧或隐藏上下文才能回答的地方。可以阻塞相关任务与集成；management agent 审阅时遇到需要人类判断的决策，也会主动开一个问题并暂停合并，而不是擅自决定。
06

系统设计

存储：一切长在项目文件夹里

一个项目 = 一个本地文件夹 + 一个 Git 仓库。知识文件（orbital/PROJECT_STATE.md、DECISIONS.md、LESSONS.md、INDEX.md）与工作产物一起进版本管理，随仓库携带与迁移；任务、问题、收件箱、事件日志等运行时状态存放在 .git/orbital-team/，同一仓库的所有 worktree 天然共享，且永不外发。没有数据库，没有云端依赖——上下文的物理形态就是文件，任何工具都能读。

角色：成员 agent 与 management agent 的分工

  • 成员 agent：身份绑定在独立 worktree 上（分支 member/<id>），认领任务、在自己的分支上工作、提交带验证证据的报告。成员从不直接 merge、从不直接改团队记忆。
  • Management agent：唯一的合并者与知识维护者。审阅报告 → 守卫式 merge（或退回修改、或阻塞并开问题）→ 将合并结果编译为知识提案 → 校验后落库。全程只能通过受控命令改变状态，哈希守卫防止覆盖并发修改。
  • 守护进程（daemon）：监听事件，把已提交的报告转为集成任务；对无头模式的项目自动唤起 management agent（Claude Code / Codex 无头运行，复用本机已有登录，一次登录全局生效）。管理面板一键启停，也可完全手动驾驶。

接入：任何 agent，装插件即入场

从管理面板复制一条接入消息，粘贴到任意 agent 会话：agent 自动建立 worktree、绑定成员身份、安装 /team 指令集，然后向用户简报工作方式。对不支持插件的 agent，提供等价的中立 CLI（teamctl）——协议在文件与命令层，不在某家 agent 里。

守卫机制：为什么这份记忆烂不掉

  • 只有一个写入者。团队记忆只接受 management agent 的全文件提案，且带基线哈希校验——并发修改会被识别为过期而非被覆盖。
  • 知识有淘汰纪律。编译契约明确要求：现状文件只保留当下为真的事实，替换过期内容，禁止追加流水账；决策要有依据，经验要可复用、要去重。
  • 人保留裁决权。互相矛盾的结论、缺失授权的决策，一律阻塞并转为开放问题，等人回答后再继续——管理 agent 从不替团队拍板。
  • 面板只在本机回环端口服务，写操作绑定启动时声明的身份，请求来源经校验，运行日志永不离开本机。
07

部署形态：本地 demo 与云端生产形态

当前仓库是一个本地 demo：单机、文件运行时、回环管理面板。它的使命是验证协议与闭环——四类上下文、守卫合并、知识编译、插件接入，这些已全部跑通。生产级的做法是云端化，包含两个托管组件：

云端团队空间

托管的项目上下文——任务、问题、收件箱、知识与产物存储。团队成员经身份认证接入，不再依赖某台机器的文件系统；跨时区、跨设备共享同一份项目状态。

云端 Management Agent

常驻托管运行：always-on 收集 IM 讨论，按事件即时执行守卫合并与知识编译——不依赖任何人的笔记本开机，服务可用性由平台保证。

迁移路径是平滑的：本地 demo 已经把上下文物化为文件、把状态变更收敛为受控命令，云端化 = 替换存储层与 runner 宿主，概念模型与协议不变。成员 agent 仍在各自的本地环境工作，通过同一套协议与云端空间交互；本地模式保留为离线 / 私有化选项。

08

用户旅程

  1. 建项目在管理面板选择任意本地文件夹新建项目；非 Git 文件夹自动初始化，守护进程随项目自动启动。
  2. 接入成员复制成员接入消息，粘贴进任意 agent 会话；agent 自建 worktree、绑定身份，并向成员简报工作方式。
  3. 喂入讨论群聊记录经沉淀进入收件箱，人分诊后提升为代办或转为问题。
  4. 认领与执行成员 agent 以团队知识为背景认领任务，在自己的 worktree 里工作、本地提交。
  5. 提交报告完成后提交结构化报告：摘要、验证证据、风险与知识候选。
  6. 守卫合并management agent 被自动唤起：审阅 → 合并 / 退回 / 阻塞提问。产物进入团队主干。
  7. 知识沉淀合并结果被编译进团队记忆，过期事实被替换；下一个任务、下一个 agent，从更新后的上下文出发。

以投行尽调为例。群里讨论「目标公司的关联交易要再核一遍」，沉淀 agent 将其提炼为候选任务进入收件箱；负责人分诊后设为就绪。分析师的 agent 认领任务，先读团队知识——上一轮已核实的股权结构、已定的口径决策——然后只做增量核查，提交带来源引用的报告。management agent 审阅时发现两份材料对同一笔交易金额记载不一致，于是阻塞合并、开出问题：「以年报口径还是尽调底稿口径为准？」合伙人在面板上一句话拍板，集成自动继续，结论与口径决策一并写入团队记忆。下一位接手的同事（或 agent），直接站在这份记忆之上。管理咨询、法律文书、政策研究等文本密集型协作，同理。

09

现状校准：设计 vs 实现

以下对照当前代码库逐项核对。核心闭环——代办、问题、知识编译、守卫合并、插件接入、管理面板——已实现并经端到端实测（包括无头 management agent 在真实项目上审阅报告、主动阻塞并向人提问的完整链路）。

设计点状态说明
项目粒度已实现本地文件夹 + Git 仓库；面板一键创建（含自动 git init）；跨文件夹项目注册表。
代办已实现完整状态机与看板；原子认领；拖拽放行（Backlog → Ready）。
开放问题已实现阻塞语义、回答/搁置/关闭；management agent 审阅遇疑主动开问题。
知识沉淀已实现四份记忆文件 + 索引；全文件提案、哈希守卫、校验后落库；面板可见变更。
守卫合并已实现merge / 退回 / 阻塞三条出路；禁止原始 git 写操作；报告绑定提交哈希。
插件接入已实现Claude Code（/team + 会话钩子）、Codex、通用 CLI；接入消息一键复制。
Management agent 无头运行已实现守护进程按事件唤起 Claude Code / Codex 无头执行；复用本机登录；面板一键启停，随项目自动启动。
讨论沉淀（IM 接入）规划中收件箱与分诊流程已就绪，摄入端目前仅支持样例数据源；真实 IM CLI 接入与 always-on 定时沉淀是下一步重点。
云端团队空间 + 云端 management agent规划中当前为本地 demo；生产形态见第 07 节——协议不变，替换存储层与 runner 宿主。
10

路线图

  1. IM 接入与 always-on 沉淀：接通企业微信 / Slack 等 IM CLI，支持用户触发与定时两种模式，把群聊持续提炼进收件箱——补齐闭环的入口。
  2. 云端团队空间与云端 management agent：托管项目上下文与常驻维护者，使分布式团队共享同一份项目空间；本地模式保留为离线 / 私有化选项。
  3. 更深的 agent 集成：基于 Claude Agent SDK 与 Codex app-server 的常驻 management agent 运行器，降低冷启动、增强可观测性。
  4. 知识消费面：面向成员 agent 的知识检索与订阅接口，让「站在团队记忆上工作」成为每个任务的默认起点。
